# IA462 Midterm: Host, Container, and Supply-Chain Security

## What this repository contains

This repository contains my IA462 midterm implementation and evidence for hardening Ubuntu under WSL, establishing a Windows security baseline, and building a Flask application in a restricted Docker container. I collected configuration files, terminal transcripts, Windows events, vulnerability reports, an SPDX software bill of materials, and screenshots. The GitHub workflows build the application, scan its image, generate SBOMs, and audit its Python dependencies. The project demonstrates both a successful main-branch build and a deliberately vulnerable pull request whose security checks fail. This is a lab deployment, and the evidence identifies the remaining limitations instead of treating a passing check as proof that the system is completely secure.

## Cross-platform hardening comparison

| Area | Linux / WSL Ubuntu | Windows host | Docker application |
| --- | --- | --- | --- |
| Kernel model | Linux uses a monolithic kernel with modules. This Ubuntu installation runs under WSL 2. | Windows uses the NT hybrid kernel. The Windows host and the WSL Linux environment have different kernels. | The Linux container shares the Docker host's Linux kernel. Its image supplies user-space libraries, not a separate guest kernel. |
| Access control | Users, groups, file modes, umask, PAM, sudo, and SSH policy | SIDs, access tokens, NTFS ACLs, local security policy, and Defender | Non-root UID/GID 999, namespaces, dropped capabilities, no-new-privileges, a read-only root filesystem, and a custom seccomp filter |
| Auditing | Terminal transcript, systemd service state, authentication tests, Lynis, and kernel audit messages | Security events, process command-line auditing, PowerShell script-block logging, and Sysmon | Container inspection, application output, syscall tracing, runtime security fields, and seccomp audit messages |
| Hardening standard | CIS Linux/Ubuntu and relevant STIG guidance provide reference baselines; the lab applies selected controls and uses Lynis for assessment. | Microsoft security baselines, CIS Windows guidance, and relevant STIG guidance provide reference baselines; the lab verifies selected settings with PowerShell. | Docker Bench evaluates CIS Docker Benchmark checks. A daemon configuration sample is supplied separately. |
| Common attack surface | Remote access, weak authentication, unnecessary services, SUID programs, and writable files | Accounts, PowerShell, SMB, applications, privileged processes, and antivirus exclusions | Base-image packages, Python dependencies, the application endpoint, runtime privileges, the Docker daemon, and build workflows |

The three environments require different configuration tools, but they share the goals of reducing privilege, limiting exposed services, and collecting useful evidence. Container restrictions depend on the host kernel and do not replace host hardening or package updates. The standards in the table are reference frameworks, not claims of complete CIS or STIG compliance.

## Implementation and measured results

- **Section 1, Linux:** `ia462student` belongs to `ia462lab` without sudo membership. A new login with umask `027` produced a file with mode `640` and a directory with mode `750`. `apport` and `landscape-client` changed from enabled to disabled; both were already inactive before the change. SSH disables root login and empty passwords and limits authentication attempts to three. PAM and `faillock.conf` enforce five failures with a 900-second observation interval and a 600-second unlock time. The transcript records failed authentication, lockout, reset, and a successful login. Lynis reported a hardening index of **67** across **258 tests**. [Linux evidence](section1/linux-hardening-transcript.txt)
- **Permission inventory:** The full scan recorded **63 SUID paths**, **189,495 world-writable paths**, and **397 error lines**, returning exit status 1. Of the writable paths, 188,609 were under `/mnt/c`; the other 886 include virtual `/proc` and WSLg files. Windows mount permission failures, a WSLg filesystem loop, and disappearing `/proc` entries limit coverage. WSL-reported permission bits are not a complete assessment of Windows ACLs. [Scan scope and limitations](section1/permission-scan-notes.txt)
- **Section 2, Windows:** Defender, real-time protection, and tamper protection were enabled; all three firewall profiles were enabled; SMBv1 was disabled; and Sysmon64 was running with automatic startup. Command-line auditing and script-block logging were enabled. The export contains **100 Security events**, while the separate **12-event test export** contains IDs 4624, 4625, 4688, 4720, and 4104. The temporary `ia462midterm` account was deleted after testing. The application-directory Defender exclusion was configured for the assignment and reduces scanning coverage for that directory. [Windows transcript](section2/windows-transcript.txt) and [test events](section2/midterm-test-events.json)
- **Sections 3 and 4, container and initial scan:** The image uses a digest-pinned Python base, a builder and non-root runtime, and a hash-verified Python lock. The initial hardened image's Trivy report contained **155 Critical/High/Medium package findings: 0 Critical, 54 High, and 101 Medium**. Grype reported **249 package-finding rows**, including 84 High. Repeated CVEs across packages are not separate unique vulnerabilities. The [CVE write-up](section4/cve-writeup.md) examines CVE-2026-19499 and explains the scanners' differing severity ratings.
- **Section 5, policy:** The corrected Docker Bench run completed **117 checks**, reported a score of **17**, and returned exit status 0. That score is not a compliance percentage. The [Sigma rule](section5/windows-local-account-created.sigma.yml) selects Security event 4720 and maps local account creation to **T1136.001**. The observed event was an authorized lab test; it demonstrates a matching event type, not an intrusion or a deployed SIEM detection.
- **Section 6, remediation and retest:** The revised common Docker base stage installs available Debian updates. Recorded versions include `libc6` and `libc-bin` **2.41-12+deb13u5** and `zlib1g` **1:1.3.dfsg+really1.3.1-1+deb13u1**. The patched `ia462-midterm:ci-ready` image passed its local Trivy gate and ran as UID/GID 999 with GET `/` **200**, HEAD `/` **200**, and GET `/missing` **404**. [Patch versions](section6/patched-os-packages.txt), [runtime results](section6/ci-runtime-test.txt), and [successful main CI run](https://github.com/Whendul/ia462-midterm-wumadhay/actions/runs/45293922167)

Section 4 retains the original image's scan and SBOM. Section 6 contains the patched image's later evidence. The final [run command](section3/run-command.sh) uses the tested `ci-ready` image on `127.0.0.1:5002`; earlier Section 3 screenshots show the original image on port 5001.

## Supply-chain threat model

| Attacker attempt | Implemented control and its effect | Evidence and limitation |
| --- | --- | --- |
| Replace a floating container tag or third-party Action release with different code | The base image is pinned by SHA-256 digest, and every directly referenced third-party Action uses a full commit SHA. These references prevent silently selecting new content under the same tag. | [Dockerfile](Dockerfile), [workflow](../.github/workflows/security-pipeline.yml). A pin does not establish that its selected content is trustworthy. Slide: **Pinning vs. Floating Dependencies**. |
| Substitute a Python distribution or introduce an unexpected dependency version | Exact pins and the complete generated lock select versions; `pip install --require-hashes --only-binary=:all:` rejects distributions whose hashes do not match the lock. | [requirements.txt](requirements.txt), [requirements.lock](requirements.lock). Initial selection and lock updates still require review, including package names and provenance. Slides: **Dependency Confusion & Supply Chain Attacks** and **Pinning vs. Floating Dependencies**. |
| Add a dependency with a known serious vulnerability | Dependency Review fails newly introduced High/Critical advisories. pip-audit checks both the direct requirements and hashed lock. Trivy fails fixable High/Critical image findings. Dependabot checks pip, Docker, and Actions weekly. | [Dependabot](../.github/dependabot.yml), [Dependency Review](../.github/workflows/dependency-review.yml), [PR #4](https://github.com/Whendul/ia462-midterm-wumadhay/pull/4). Required status checks provide merge enforcement; a red check alone does not establish that merging is blocked. Slides: **GitHub Dependency Security Tools**, **GitHub's Dependency Review Action**, and **Integrating Dependency Scanning into CI/CD**. |
| Abuse a workflow's repository credentials or change security gates through a pull request | Workflow permissions are limited to `contents: read`, checkout does not persist credentials, and Action versions are pinned. Branch protection and review are the repository controls for enforcing checks and reviewing workflow changes. | [Pipeline](../.github/workflows/security-pipeline.yml) and [gate demonstration status](section6/pr-gate-status.md). A compromised authorized maintainer or an approved malicious dependency remains a risk. Slide: **Securing Dependencies in GitHub Actions**. |
| Hide vulnerable transitive or operating-system components | Syft records the image's package inventory in SPDX JSON. Grype scans that inventory, and CI generates SPDX, CycloneDX, and readable SBOM artifacts for the image it built. | [Baseline SPDX SBOM](section4/sbom.spdx.json), [Grype results](section4/grype-report.txt), [CI workflow](../.github/workflows/security-pipeline.yml). An SBOM improves visibility; it does not itself block execution. Slide: **Software Bill of Materials (SBOM)**. |
| Turn application compromise into broader host or container changes | UID 999, a read-only root filesystem, dropped capabilities, no-new-privileges, loopback-only port publication, and seccomp reduce available privileges and operations. Windows auditing and the Sigma selection support investigation of account creation. | [Run command](section3/run-command.sh), [seccomp notes](section3/seccomp-notes.md), [runtime evidence](section6/ci-runtime-test.txt), [Sigma rule](section5/windows-local-account-created.sigma.yml). These controls limit impact but do not repair vulnerable code or prove that exploitation is impossible. |

The Week 8 slide titles above identify the course material used for the threat model. The main-branch pipeline and the deliberately vulnerable PR provide contrasting examples: the main run succeeds, while PR #4's Dependency Review, pip-audit, and Trivy checks fail and its build and SBOM jobs succeed. The PR's final closure and merge-blocking evidence are tracked in [pr-gate-status.md](section6/pr-gate-status.md).

## Limits and evidence handling

Lynis reported an older-tool notice and no matching OS end-of-life database entry; neither establishes that the OS is unsupported. The daemon settings are a sample, not an applied global configuration. Docker Bench still reports issues including missing host audit rules, daemon defaults, AppArmor coverage, resource limits, and health checks. The Flask development server is used only for this lab. The seccomp profile includes documented runtime compatibility allowances and is not claimed to be a mathematically minimal policy.

A green Trivy gate means no fixable High/Critical findings matched that gate's policy, not that all severities are clear. Debian updates come from repositories at build time, so the final image is not bit-for-bit reproducible across dates despite the pinned starting image. Reports are dated observations, and future vulnerability databases can produce different results.

Text exports have documented identity redactions, with event counts, test outcomes, package versions, and scan counts preserved. Screenshots are retained as supplied. [Evidence handling details](EVIDENCE-NOTES.md)
